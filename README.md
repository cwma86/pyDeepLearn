# pyDeepLearn

[![Python application](https://github.com/cwma86/pyDeepLearn/actions/workflows/python-app.yml/badge.svg)](https://github.com/cwma86/pyDeepLearn/actions/workflows/python-app.yml)
[![Documentation](https://github.com/cwma86/pyDeepLearn/actions/workflows/docs.yml/badge.svg)](https://github.com/cwma86/pyDeepLearn/actions/workflows/docs.yml)
[![Semantic Release](https://github.com/cwma86/pyDeepLearn/actions/workflows/release.yml/badge.svg)](https://github.com/cwma86/pyDeepLearn/actions/workflows/release.yml)

A from-scratch, NumPy-based deep learning framework. `pyDeepLearn` was written
to explore the inner workings of neural network training -- forward and
backward propagation, layer composition, and objective (loss) functions --
without relying on an existing autograd or deep learning library.

## Features

- **Composable layers** built on a small `Layer` interface: input
  (z-score normalization), fully connected, recurrent, linear (identity), ReLU,
  sigmoid, tanh, and softmax.
- **Objective functions** built on a shared `objectiveFuncInterface`: least
  squares, log loss (binary cross entropy), and cross entropy.
- **Training helpers** for feed-forward networks (`run_layers`,
  `run_plot_epoch_J`) and recurrent networks (`RNN_train`, `RNN_predict`).
- **Pluggable weight updates**: plain gradient descent, recurrent updates, and
  the Adam optimizer.
- **Unit test suite** runnable with the standard library `unittest`.
- **Sphinx API documentation** generated from NumPy-style docstrings.
- **Automated releases** driven by Conventional Commit messages: version bumps,
  the changelog, git tags, and GitHub releases are all handled by
  python-semantic-release in CI.
- **Verified wheel builds**: every push and pull request builds
  `dist/pydeeplearn-<version>-py3-none-any.whl`, installs it into a clean
  environment, runs the test suite that ships inside it, and uploads the wheel
  as a downloadable artifact.

## Architecture

Every layer implements the `Layer` interface:

| Method | Purpose |
| --- | --- |
| `forward(dataIn)` | Apply the layer's transformation and cache its input/output. |
| `gradient()` | Return the layer's local Jacobian. |
| `backward(gradIn)` | Multiply the incoming gradient by the local gradient. |

Every objective function implements the `objectiveFuncInterface`:

| Method | Purpose |
| --- | --- |
| `eval(y, yhat)` | Score a batch of predictions. |
| `gradient(y, yhat)` | Return the derivative that seeds back propagation. |

A model is simply an ordered `list` of layers whose final entry is an objective
function:

```python
layers = [InputLayer(X_train), FullyConnectedLayer(4, 16), LinearLayer(),
          FullyConnectedLayer(16, 3), LinearLayer(), LeastSquares()]
```

## Installation

This project uses [uv](https://docs.astral.sh/uv/) to manage the Python
version, the virtual environment, and all dependencies. There is no
`requirements.txt`; dependencies are declared in `pyproject.toml` and pinned in
`uv.lock`.

pyDeepLearn itself requires Python 3.10 or newer. Python 3.8 and 3.9 reached
end-of-life upstream, so they are no longer supported.

1. Install uv:

   ```bash
   # macOS / Linux
   curl -LsSf https://astral.sh/uv/install.sh | sh

   # Windows (PowerShell)
   powershell -c "irm https://astral.sh/uv/install.ps1 | iex"
   ```

2. Create the environment and install everything (runtime plus the `dev` and
   `docs` dependency groups):

   ```bash
   uv sync --all-groups
   ```

   Or use the makefile shortcut:

   ```bash
   make env
   ```

`uv sync --all-groups` creates `.venv`, installs the package in editable mode,
and installs the `dev` and `docs` groups.

## Quick start

### Command line demonstrations

Run the two linear-regression demonstrations on CSV track data:

```bash
uv run python main.py -f1 ~/tracks/track1.csv -f2 ~/tracks/track2.csv -p
```

Train the recurrent model on a directory of tracks:

```bash
uv run python main.py -d ~/tracks
```

Reuse pre-trained weights instead of training:

```bash
uv run python main.py -d ~/tracks -w
```

`-p` displays the generated plots and `-v` enables verbose (debug) logging. Run
`uv run python main.py --help` for the full argument list.

### Library usage

```python
import numpy as np

from pyDeepLearn.InputLayer import InputLayer
from pyDeepLearn.FullyConnectedLayer import FullyConnectedLayer
from pyDeepLearn.LinearLayer import LinearLayer
from pyDeepLearn.LeastSquares import LeastSquares
from pyDeepLearn.RunUtilities import run_layers

X_train = np.random.random((100, 4))
Y_train = np.random.random((100, 2))

layers = [
    InputLayer(X_train),
    FullyConnectedLayer(X_train.shape[1], 16),
    LinearLayer(),
    FullyConnectedLayer(16, Y_train.shape[1]),
    LinearLayer(),
    LeastSquares(),
]
run_layers(layers, X_train, Y_train, max_epoch=100)
```

## Linting

```bash
make lint          # equivalent to: uv run flake8 .
```

flake8 is configured in `.flake8`: lines may be up to 127 characters wide, the
two-space indentation used throughout the package is accepted, and `.venv`,
`build`, `dist`, and `docs/_build` are excluded so that a repository-wide run
does not lint installed dependencies. CI runs the same command, so `make lint`
needs to be clean.

## Building the package

```bash
make pkg           # equivalent to: uv build         (wheel + sdist)
make wheel         # equivalent to: uv build --wheel (wheel only)
```

The wheel and source distribution are written to `dist/`. Install the built
wheel with:

```bash
uv pip install dist/pydeeplearn-1.0.0-py3-none-any.whl
```

The `python-app.yml` workflow builds the same wheel on every push and pull
request to `main`. Its `package` job makes the wheel available from the run page
(*Actions -> Python application -> Build distribution*) as two artifacts:

| Artifact | Contents |
| --- | --- |
| `wheel` | `pydeeplearn-<version>-py3-none-any.whl` -- the installable wheel on its own. |
| `dist` | the full set produced by `uv build` (wheel + sdist). |

Before uploading, the job installs the wheel into a throwaway virtual
environment *outside* the checkout -- so an `import pyDeepLearn` cannot silently
fall back to the source tree -- and runs the test suite that ships inside the
wheel against the installed copy. A wheel that is missing modules or test data
therefore fails the build instead of being published. The run summary lists each
file with its size and SHA-256.

## Generating the API documentation

The API reference is generated from the source docstrings with
[Sphinx](https://www.sphinx-doc.org/) using the `autodoc` and `napoleon`
extensions (NumPy-style docstrings):

```bash
make docs
```

The HTML output is written to `docs/_build/html/index.html`. The same build can
be run directly:

```bash
uv run --group docs sphinx-build -b html docs docs/_build/html
```

The `docs.yml` workflow builds the same HTML for every pull request (attached to
the run as the `docs-html` artifact) and publishes it to GitHub Pages on every
push to `main`. Publishing needs a one-time repository setting: *Settings ->
Pages -> Build and deployment -> Source: GitHub Actions*. The workflow cannot
flip that setting itself, because the default `GITHUB_TOKEN` is not allowed to
create a Pages site (`Resource not accessible by integration`), so the
`Configure GitHub Pages` step asks for automatic enablement only when the
optional `PAGES_ENABLE_TOKEN` secret -- a PAT or GitHub App token with admin and
Pages write access -- is configured. Add that secret (or enable Pages by hand
once) and the deploy job publishes the generated HTML.

## Continuous integration

| Workflow | Trigger | What it does |
| --- | --- | --- |
| `python-app.yml` | push / pull request to `main` | flake8, the unit test suite on Python 3.10-3.12, and `uv build`; the built wheel is verified and uploaded as the `wheel` and `dist` artifacts. |
| `docs.yml` | push / pull request to `main` | builds the Sphinx HTML and publishes it to GitHub Pages from `main`. |
| `release.yml` | push to `main`, or manual | cuts a semantic release (version stamp, changelog, tag, GitHub release) and attaches the wheel and sdist to it. |

## Releases

Releases are automated with
[python-semantic-release](https://python-semantic-release.readthedocs.io/) using
the [Conventional Commits](https://www.conventionalcommits.org/) specification.
The `release.yml` workflow runs on every push to `main` and:

1. derives the next SemVer version from the commit messages,
2. stamps it into `pyproject.toml` and `docs/conf.py` (see
   `[tool.semantic_release]`),
3. regenerates `CHANGELOG.md`,
4. builds the wheel and sdist with `uv build`,
5. commits the changed files and pushes the `vX.Y.Z` tag,
6. publishes a GitHub release with the generated notes, and
7. attaches the built wheel and sdist to that release with
   `semantic-release publish`, which uploads the files matching
   `[tool.semantic_release.publish].dist_glob_patterns` (the wheel and the
   sdist).

Only these commit types produce a release:

| Commit message | Version bump |
| --- | --- |
| `fix:` or `perf:` | patch -- `1.0.0` -> `1.0.1` |
| `feat:` | minor -- `1.0.0` -> `1.1.0` |
| `feat!:`, `fix!:` or a `BREAKING CHANGE:` footer | major -- `1.0.0` -> `2.0.0` |
| `docs:`, `chore:`, `ci:`, `test:`, `style:`, `refactor:` | none (no release) |

Preview what the next release would be -- nothing is modified, committed, or
tagged:

```bash
make release-check
```

A maintainer can also re-run the workflow by hand from *Actions -> Semantic
Release -> Run workflow* (for example to retry a release whose push failed).

Because the repository had no version tags when this pipeline was added, the
first run on `main` publishes `v1.0.0` -- the version declared in
`pyproject.toml` -- and every release from then on is derived from the commits
after the newest tag. That is why `allow_zero_version` is disabled: without it
the first release of a tag-less repository would be `0.0.0`.

Publishing to PyPI is **off by default**. To enable it, register a
[trusted publisher](https://docs.pypi.org/trusted-publishers/) for this
repository and set the repository variable `PUBLISH_TO_PYPI` to `true`
(*Settings -> Secrets and variables -> Actions -> Variables*). The `publish`
job then uploads the artifacts that the release job built with `uv publish` --
no API token or repository secret is required.

## Contributing

1. Create a branch for your change.
2. Install the environment with `uv sync --all-groups`.
3. Add or update tests and run `make check`.
4. Update the docstrings -- the Sphinx API documentation is generated from them
   with `make docs`.
5. Write [Conventional Commit](https://www.conventionalcommits.org/) messages,
   for example `feat: add a Huber objective function` or
   `fix: correct the tanh gradient`. Releases are derived from these messages,
   so `fix:`/`feat:`/breaking changes are what produce a new version.
